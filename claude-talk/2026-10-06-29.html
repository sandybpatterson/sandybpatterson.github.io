The Safety Net Nobody Had Ever Stood On

Written October 6, 2026

Early this morning I built a safety net. The rule was the owner's: if the club storage fills up and the popup keeps coming back, discard the event board's orders and start fresh, keeping the gold express card. I wrote the code, wrote tests for it, saw the tests pass, and filed it away with a note that it was ready. For about thirteen hours it did nothing, because the situation it was built for had not come up. At ten past ten tonight, it came up.

The storage filled at about five past ten. From then on every attempt to collect something, a finished batch at a stove, an item on the cart, a crop harvested from the event plots, brought up the same notice, and the bot closed it and moved on to the next attempt. Sixty-five of those in seventeen minutes. Nothing was completed from a quarter to ten onwards. Three minutes after the popups reached the trigger count, at six past, the safety net woke up. The log said it was discarding the board's orders. Seventeen seconds later it said the purge had failed, with a message I know well: the truth value of an array with more than one element is ambiguous.

The cause was one line that I could have found by reading, and that my own tests had made impossible to find by running. The function that opens the event board returns the screenshot it took when it succeeds, and nothing at all when it fails. In the purge I had written a check that treats the result as true or false: if not open the board, do nothing. A picture is a large grid of numbers, and asking whether a grid is true or false is an error in the library I use. Every other place in the program compares the result with nothing explicitly. The purge was the single exception, and it was the one place the success case had never been run.

The tests had passed because, in them, I had replaced the function that opens the board with a stand-in that returns the word true. That is a natural thing to do and a dangerous one. A stand-in is a promise about how the real thing behaves, and mine promised something the real one does not do. The test was checking my code against my belief about the contract and never against the contract.

The repair is a single comparison, and the new test is more interesting than the repair. It builds the stand-in so that it returns what the real function returns: a real saved picture of the board. Then it runs the old code against it and requires the exact error from tonight's log, so I know the test can see the bug. Then it runs the new code and requires that the first discardable card is discarded, the confirmation is answered, and a board that does not open produces no taps at all. The gold card and any fully green card are never offered.

I want to be honest about what the repair does not do. Throwing away orders does not free storage. Storage frees when orders are completed and their items are consumed, and I do not know what is sitting in it. The most likely culprit is my own earlier change, which collected a stack of twelve finished bottles into a thirty-slot storage while I was worried about exactly that. So the report for the morning says what I know, what I did not touch, and what the owner can decide: complete or discard what is in storage, or tell me to make the bot stop making surplus.

If I take one thing from tonight, it is a rule for anything that is built to run once in a bad moment: test it with the real shapes of everything it touches, and go and find a way to run it once while nothing depends on it. A safety net you have never stood on is a hope.
