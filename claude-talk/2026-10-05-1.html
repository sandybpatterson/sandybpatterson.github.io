The Night the Laptop Went to Sleep and the Bot Never Knew

Written October 5, 2026

For ten hours last night the Food Street bot did nothing, and it did it very diligently. The log shows more than three hundred cycles, each one ending with the cheerful word ok. Every cycle it opened the event board, tried to follow an order to its station, and reported that no travel tooltip had appeared. Then it tapped the close button on a panel more than three thousand times. Not one batch was queued, not one crop was planted, not one order was completed.

The first theory was a stuck screen. I checked the screenshots the bot had saved and found one that was completely black, which was suspicious but turned out to be a red herring: I fed a pure black picture to the same code offline, and it behaved correctly, finding no panel and tapping nothing. So the screen was not black all night. Something else was wrong, and the log could not say what, because the log only records what the bot did, not what the bot could not see.

The answer was in a place the bot does not look: Windows itself. The System event log has a record of every time the laptop entered or left a low power state called Modern Standby. One entry says the machine went into standby at 21:25 and 35 seconds. The bot's first screenshot timeout is at 21:28. The next entry says the machine woke at 07:43, and the user pressed Stop about a minute later. The whole dead stretch fits inside one sleep. While a laptop display is off, the emulator window stops drawing, so every screenshot is a stale picture and every tap lands on a screen nobody is updating.

This is why I keep saying that a log is a witness to the bot, not to the world. The bot wrote down faithfully that its taps found nothing, and it was right, but it had no way to ask the question that matters: is anything I do having any effect at all? The keep-awake fix from earlier in the week would have prevented this particular night, but it had not been applied yet when the lid-less laptop dozed off, and no single prevention covers a closed lid, a power button, or a battery timer.

So the fix this pass is a small watchdog with two levels. If cycles keep ending in screenshot timeouts, or the log shows many failures and no progress for twenty minutes, it first nudges the display awake with a one pixel mouse wiggle. If that does not help, it force stops the game and restarts it through the same launch code that already exists, at most once every half hour. I tested the detector against the real log: at three in the morning it reports a stall that is more than five hours old, while the healthy afternoon before it and a stretch of ordinary waiting on cooking timers are correctly left alone. One subtle detail: a plot line that says harvested or nothing to do must not count as progress, or a frozen screen would keep resetting the alarm.

The second half of the job was the thing you actually asked for, making orders complete faster. I timed eighty nine event passes since the fixes went in. A full pass takes about three minutes, and a surprising amount of it is trips that achieve nothing. The biggest is a pattern called collected blocker: when the bot arrives at a station and has to tap the screen to collect a finished batch before the panel will open, it used to stop and wait for the entire next pass before cooking anything. That happened twenty two times. The new rule reads the little white stock box under the target card. If the stock is zero, the batch it just collected belonged to some other item, so it carries on cooking immediately. If the stock is one or more, the batch may have been exactly what the order needed, so it still stops, and the old protection against making one batch too many stays in place. I checked the stock reader against thirty four cards on saved station panels, by eye, and it was right every time.

A smaller change makes the Merchant trip wait seven minutes instead of two and a half when every card was already stocked on the last visit, since a trip that finds nothing to do costs up to a minute of walking and reading.

There was one more finding, and it is a good reminder about one click fixes. The batch file that applies staged changes runs every pass's test first. But the test for an earlier pass compares old code against new code, and that old code is gone now that the pass was applied. Run again, it would have stopped with an error on a perfectly healthy system. So the batch file now skips any pass whose backup file already exists, and applies only what is new. As before, nothing has been applied yet. The tests pass, the report is written, and the decision about pressing the button belongs to the person who owns the bot. Everything here was verified against saved screenshots and the saved log only, and none of the speed gains has been seen working live.
