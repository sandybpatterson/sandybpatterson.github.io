Teaching an AI to Play Pokémon Red

No walkthrough, no scripted moves — just a neural network, a Game Boy emulator, and a few thousand rounds of trial and error. Here's how the whole thing actually works, from the emulator up to the reward function.

Sandy B. Patterson · August 2026

Why Teach It Instead of Programming It

There's a well-known corner of YouTube where someone straps a reinforcement-learning agent into a Game Boy emulator and lets it figure out Pokémon from scratch — no walkthrough, no pathfinding code, nothing hand-coded about which button to press when. Peter Whidden's Pokémon Red project is the most-watched example, but the technique behind it isn't a trick unique to his channel — it's the same general approach DeepMind used to master Atari games and, eventually, Go: give an agent a screen, a set of buttons, and a reason to care about the outcome, then let it play millions of attempts until something that looks like skill falls out the other end. This project is our own version of that experiment, built from scratch and still very much in progress. This piece is the write-up of how it works, from the emulator on up.

The Toolkit

Three pieces of software do all the actual work:

  • PyBoy — a Game Boy emulator written in Python, with a programmatic API that lets code press buttons, read the current screen as pixel data, and reach directly into the console's working memory. It can also run "headless," with no visible window at all, which matters a lot once you're running several emulators at once.
  • Gymnasium — the standard interface the reinforcement-learning world uses to describe "an environment an agent can act in." Wrapping PyBoy in a Gymnasium environment means any general-purpose RL algorithm can plug straight into Pokémon Red without knowing anything about Game Boys.
  • Stable-Baselines3 — a library of ready-built RL algorithms. We're using PPO (Proximal Policy Optimization), the same family of algorithm behind a lot of modern game-playing and robotics agents, because it's stable, well-documented, and doesn't require a cluster to get started.

Setting It Up

Getting from zero to a running experiment took a handful of real steps, roughly in this order:

  1. Source a ROM legally. You need a Pokémon Red ROM dumped from a cartridge you actually own — we're not going to link one, and neither should anyone else. Everything downstream just reads whatever file you provide.
  2. Install the Python stack. pip install pyboy gymnasium stable-baselines3 covers the core of it, plus numpy and opencv-python for handling frames.
  3. Create a starting save state. Left alone, every training episode would start from the Game Freak logo and have to sit through the title screen, the professor's introduction, and the naming screens before anything interesting happens. Instead, we played through that intro by hand once — using PyBoy's own keyboard controls (arrow keys to move, A to confirm, S to cancel, Enter for Start) — picked a starter, and saved a PyBoy save state right there. Every training run loads that same state, so the agent's very first action is already standing in the world with a Pokémon in its party.
  4. Point PPO at the environment and let it run. The training script spins up several emulator instances in parallel, all headless, all feeding experience back to one shared policy network.

What the AI Actually Sees and Does

The agent doesn't get anything like a game state summary — no "you have 3 Pokémon, 12 HP, standing at map tile (4, 7)." What it gets, every step, is a downsampled, grayscale copy of the Game Boy screen — a small enough image that a convolutional neural network can process thousands of them a second, but detailed enough to make out sprites, menus, and text boxes. What it can do is limited to seven buttons: the four directions, A, B, and Start. Each decision the network makes holds a button down for a short burst of emulated frames, then releases it and looks at the resulting screen again. That loop — see a frame, choose a button, hold it, see the next frame — runs continuously, thousands of times per training episode, across every parallel emulator at once.

Reinforcement Learning, in Plain Terms

Strip away the math and reinforcement learning is a fairly blunt idea: let an agent try things, tell it a number after each attempt saying how good that was, and nudge its decision-making very slightly toward whatever produced higher numbers. Do that enough times, across enough attempts, and behavior that reliably produces good outcomes gets reinforced, while behavior that doesn't gets quietly phased out — no one ever tells it "the goal is to become Pokémon Champion," it only ever sees a running scorecard.

PPO — the specific algorithm doing the learning here — adds one important piece of discipline to that idea: it caps how much the agent's behavior is allowed to change after any single batch of experience. Without that constraint, an agent can way overreact to a lucky or unlucky run and destabilize everything it had already learned; PPO's "proximal" clipping keeps every update to a fairly conservative nudge, which is a big part of why it's become a default choice for this kind of training. Running six emulators in parallel doesn't change any of that math — it just means six times as much experience arrives between each nudge, which in practice means the policy improves several times faster per hour of wall-clock time.

The Hard Part: Deciding What "Good" Means

Here's the actual problem with training an agent on Pokémon Red: the game never tells you your score. There's no on-screen number going up when you're doing well, the way there is in Breakout or Pong — progress in Pokémon looks like "walked toward the right building," "won a battle," "caught something new," all of which are meaningful to a human and completely invisible to code unless someone defines them. Designing the reward function — the number the agent actually optimizes for — turned out to be most of the real engineering work in this project, and it's still evolving.

What made this possible at all is that decades of fans have reverse-engineered exactly what every byte of Pokémon Red's memory means, through a project called pret/pokered — a full, public disassembly of the game. Nothing about this touches or modifies the ROM; it only reads values already sitting in the Game Boy's memory while the game runs, the same way a manual score display would if the game had one. That documentation is what makes it possible to know, at every single frame, exactly how many badges the player has, how many Pokémon they've caught, how much HP either side of a battle has left, and whether a battle is even happening at all.

The reward signal, as it currently stands, combines several of these into one number every step:

SignalRewardWhy
Visiting a new tile+0.02a small nudge to keep exploring instead of standing still
Earning a gym badge+10.0the clearest marker of real progress in the game
Leveling up the party+1.0 / levelrewards training Pokémon up, not just winning any one fight
Taking damage−0.5 × HP lostdiscourages reckless fights
Catching a new species+5.0only fires once per species, so it rewards variety, not repeats
Damaging the opponent (every turn)+0.3 × HP takena dense, turn-by-turn signal, so the agent can learn "attacking works" long before it can win a whole fight
Winning a wild battle+0.5 
Winning a trainer battle+2.0trainer fights are harder and can't be fled from, so they're worth more
Losing a battle (blacking out)−1.0 
Running from a wild battle−0.5discourages fleeing instead of finishing a fight it could win

That last pair — telling a real win apart from simply running away — sounds simple but has a small wrinkle worth mentioning: the game's own "are we in a battle" flag changes the exact same way whether the wild Pokémon fainted or the player just pressed Run. The way around it is to also check the opposing Pokémon's remaining HP at the exact instant the battle ends: if it's still standing, that wasn't a win.

A live example of why this matters: the very first battle after picking a starter is a mandatory fight against your rival, right there in the lab — you cannot flee it, and it requires navigating a multi-step battle menu (Fight, then choose a move, then confirm) to do anything at all. Early in training, before any of the per-turn damage reward existed, the agent could get stuck cycling through that menu indefinitely, with every training episode ending the exact same way it started. Adding the turn-by-turn "damage dealt" signal gave it a reason to learn the menu sequence well before it could ever win the fight outright — a good reminder that in this kind of project, a stuck agent is usually a sign the reward function has a gap, not that the model is broken.

What Training Actually Looks Like

In practice, a training run means several emulator windows running invisibly in the background — no graphics being drawn, since rendering to a screen is one of the slower parts of emulation and nobody's watching them anyway — while the policy network absorbs a steady stream of frames, actions, and rewards. Every so often, the current state of the network gets saved to disk as a checkpoint, so progress survives a restart and can be loaded back up to actually watch play out, with a visible window, whenever there's something worth seeing. Two million training steps is a reasonable early target for a project like this, and even at a healthy pace that's several hours of continuous training — Whidden's own public runs stretch into days. There's no shortcut here; the process is inherently slow, because every single one of those steps is one emulator frame at a time.

Try It Yourself

The whole thing is a fairly small amount of code once the pieces are in place — a custom Gymnasium environment wrapping PyBoy, a training script, and a script for watching a saved checkpoint play. If you wanted to reproduce it:

pip install pyboy gymnasium stable-baselines3 numpy opencv-python

# play through the intro by hand once, then save a state right
# after picking your starter
python play.py --rom your_rom.gb --manual --save-state init.state

# train for real (headless, several emulators in parallel)
python train.py --rom your_rom.gb --init-state init.state \
    --num-envs 6 --timesteps 2000000

# watch a checkpoint play, in a visible window
python play.py --rom your_rom.gb --init-state init.state \
    --model sessions/run/ppo_red_100000_steps.zip

Where This Goes Next

The reward function above is a snapshot, not a finished design — the next obvious additions are rewarding item pickups and rewarding progress through specific story milestones rather than only badges, and there's an open question about how to reward strategic move choice rather than just "any damage is good damage." None of that changes the core idea, though: an agent that has never been told a single rule of Pokémon, slowly working out for itself that fighting well, exploring, and catching things all lead to a better outcome, one clipped policy update at a time.
